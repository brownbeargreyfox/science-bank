# Standards data layer

This directory is the authoritative content source for the question-building app. Nothing in here is
generated by AI — it's a structured transcription of official SCDE documents, kept separate from
application code so it can be versioned and updated independently.

## Layout

```
standards/
  SC/
    sources.json              <- provenance manifest: every source PDF, its role, and ingest status
    2026-2027/
      biology-1.json           <- done: all 14 Biology 1 PEs
      biology-2.json           <- done: all 12 Biology 2 PEs
      chemistry.json           <- done: all 12 Chemistry PEs
      biology-1-eocep.json     <- TODO (EOCEP item-writing constraints, separate from classroom mode)
      sep.json                 <- TODO (SEP reference library, from "Using SEPs..." guide)
      ccc.json                 <- TODO (CCC reference library, from "Using CCCs..." guide)
      biology-1-bundles.json   <- done: 6 bundles
      biology-2-bundles.json   <- done: 4 bundles
      chemistry-bundles.json   <- done: 5 bundles
```

## Bundles schema (biology-1-bundles.json, biology-2-bundles.json, chemistry-bundles.json)

Each file has `course`, `source_document`, `source_authority`, `notes`, and `bundles[]`. Each bundle
has:
- `name` — the SCDE bundle title
- `narrative` — the phenomenon-framing paragraph explaining why these PEs cohere
- `aligned_pes[]` — `{ code, partial }`; `partial: true` means the PE shares an authentic connection
  with the bundle but isn't fully met by it (SCDE's asterisk convention)
- `connected_pes[]` — PE codes from *other* courses/disciplines (Biology 2, Chemistry, Physics, Earth
  Science) that SCDE lists as sensemaking support. These are not instructional requirements and most
  are outside this app's current course scope (only Biology 1/2 and Chemistry codes resolve against
  the standards files here)
- `example_anchoring_phenomena[]` — SCDE's example real-world hooks (not exhaustive, not required)

Use a bundle to suggest a multi-standard stimulus set (e.g. a single passage or dataset that supports
questions against several `aligned_pes` at once) when a teacher's request spans related standards,
rather than generating unrelated standalone questions.

## Schema (shared across biology-1.json, biology-2.json, chemistry.json)

Chemistry PE codes use the `C-PSx-y` prefix (Physical Science domains PS1-PS4) instead of `B-LSx-y`,
otherwise the structure is identical. Biology 2 standards additionally carry a `repeat_of_biology_1: true`
flag on the 4 PEs shared with Biology 1 (B-LS1-1, B-LS3-2, B-LS3-3, B-LS4-1) — Biology 2 is not
EOCEP-assessed, so instruction on those PEs is expected to extend past the Biology 1 state assessment
boundary text; the `state_assessment_boundary` field notes this where it applies rather than silently
reusing the Biology 1 boundary.

Top-level: `course`, `standards_base`, `use_year`, `source_document`, `source_published`,
`source_authority`, `source_url`, `notes`, `domains[]`.

Each domain (`LS1`, `LS2`, ...) has `domain_code`, `domain_name`, `standards[]`.

Each standard (Performance Expectation) has:
- `code` — e.g. `B-LS1-1`
- `performance_expectation` — full official PE text (SEP bold / CCC italic / DCI regular in the source PDF; flattened to plain text here)
- `clarification_statement` — official clarification, or `null` if none
- `state_assessment_boundary` — official boundary text, or `null` if none
- `sep` — `{ name, description }`
- `dci[]` — one or more `{ code, name, text }` (primary + secondary DCIs)
- `ccc` — `{ name, description }`
- `observable_performances` — the "Observable features of student performance" bullets, grouped by the
  source document's own subheadings (these vary per PE: articulating_explanation, evidence, reasoning,
  model_components, relationships, connections, etc.) — this is the closest thing SCDE provides to
  DOK-shaping guidance and should drive question construction, not a separate invented DOK rubric
- `topics[]` — short tags for the course/topic picker UI
- `terminology[]` — SCDE's "Terminology to Support Student Discourse" list
- `question_sentence_stems[]` — optional, only included for B-LS1-1 so far; SCDE's sentence stems, useful
  as scaffolds in generated constructed-response items
- `question_family_candidate` — `true` on PEs that are strong candidates for a deterministic
  dataset/question-family generator (population data, Punnett squares, gene-frequency scenarios, etc.)
  rather than static item authoring

## Why this shape

The app must never let the LLM invent what a standard means (see project brief). Every question the
question-family engine builds cites a `code` from this file, and the "Why this question?" provenance
view in the UI reads directly from `performance_expectation`, `sep`, `dci`, `ccc`,
`state_assessment_boundary`, and `source_document`/`source_published` here — no paraphrasing at
generation time.

## Updating

When SCDE publishes new Performance Targets (they update ~yearly, most recently July 2026), add a new
year folder rather than overwriting — old questions stay linked to the standard version they were built
against. Update `sources.json` with the new document's `use_year`/`published` and set `active: true` /
`false` accordingly.

## Loading into the app

`backend/app/standards/importer.py` (run automatically at container start, or manually with
`python -m app.cli import-standards`) reads every `<STATE>/<use_year>/*.json` file read-only:
course files become `courses` + `standards` (+ `topics`), `*-bundles.json` files become `bundles`
aligned to PEs of the same course and year, and `sources.json` supplies document metadata. Rows are
matched on natural keys with a per-record sha256, so re-running changes nothing unless a file
changed, and standards are never deleted because saved questions reference them. A file that is
missing required fields, or a bundle that aligns to a PE not in its course file, stops the import
with an error naming the file.
